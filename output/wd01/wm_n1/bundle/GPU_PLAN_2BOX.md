# WM-N1 two-GPU-box plan (`bundle/GPU_PLAN_2BOX.md`)

**Owner decision (2026-10-01):** pack the WM-N1 configs onto the two rented GPU boxes with three variants: (a) all 13 configs, (b) a LEAN 9-config plan, and (c) the LEAN plan with co-run on >=48 GB cards.  Generated by `bundle.multibox`; the JSON lives in `bundle/box_configs/2box/{a,b,c}/` and loads through `bundle.multibox.load_box_configs_dir`.

## Design GPU-hour estimates (amendment 3 A3.7)

| config family | envelope (GPU-h) | point (midpoint) |
| --- | --- | --- |
| Idea A member (`member-k`) | 9-17 | 13.0 |
| variant N member (`n-member-k`) | 5-10 | 7.5 |
| held-out test (1 member, as Idea A) | 9-17 | 13.0 |

`low`/`high` apply the per-config envelope to every job; `mid` uses the midpoint.  All are design estimates to be replaced by the timing gate.

## Scheduling rules

1. Idea A `member-1` is the first job on box A.
2. `member-k` (k>1) is released only once `member-1` finishes (member-1-first, amendment 1 A1); the N family head `n-member-1` obeys the same rule inside its own family.
3. In variant (b)/(c) the held-out headline test (i) is first on box B, then (ii), (iii), then the single-member N point `n-member-1`.

## Co-run assumption (variant c only)

Variant (c) models 2-3 jobs per box on a >=48 GB card using an **explicit, documented aggregate-throughput assumption**: 2 simultaneous jobs -> **1.3x** aggregate, 3 -> **1.5x**.  A batch of n jobs therefore takes `sum(GPU-h)/speedup(n)` wall hours and each job in a batch reports the batch-completion time.  `member-1` still runs alone first; members 2-5 start only after `member-1` completes.  **This assumption is a placeholder and must be replaced by the 1-hour timing gate before any wall-clock claim.**
